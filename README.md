# Usage of this Template

## Structure of This STM32 Project Template

The structure of this STM32 project template is shown as follows:

```
├── bsp
│   ├── chips
│   │   └── stm32f1.cmake
│   ├── CMakeLists.txt
│   ├── hal_config
│   │   └── stm32f1xx_hal_conf.h
│   ├── ldscripts
│   │   └── STM32F103XE_FLASH.ld
│   ├── startup
│   │   ├── startup_stm32f103xe.s
│   │   └── system_stm32f1xx.c
│   └── svd
│       └── STM32F103.svd
├── cmake
│   ├── arm-none-eabi-toolchain.cmake
│   └── stm32-utils.cmake
├── CMakeLists.txt
├── CMakePresets.json
├── compile_commands.json
├── dependencies.cmake
├── README.md
└── src
    ├── CMakeLists.txt
    └── main.c
```

- It's managed by CMake and uses the `arm-none-eabi` toolchain to build the project. Later may add supports for other toolchains (only need to add a new toolchain file in the `cmake` folder and add more presets in the `CMakePresets.json` file).
- Dependencies like ARM CMSIS, STM32 CMSIS and STM32 HAL are managed by CMake with `FetchContent`, and they are downloaded automatically when you configure the project, those downloaded repos are under the `stm32-template/build/<preset>_deps` folder.
  - Dependencies are listed in `dependencies.cmake` file under the root directory, then two most basic interface library, i.e. `arm::cmsis` and `stm32::cmsis`, are created for all rest static libraries
- The `bsp` folder contains the board support package (BSP) files, including the startup file, linker script, HAL configuration file, and system initialization file.
  - Those files are copied from the official STM32 repos like `cmsis-device-f1`. Because those files may be modified to fit the project, they are not referenced from the library.
  - The `bsp/chips/stm32f1.cmake` file contains the chip-specific flags, and offered as a library called `bsp::mcu_config` for any compiled target to link with. If you want to use another chip, you just need to create a new CMake file and offer the same interface library `bsp::mcu_config`.
  - The `bsp/CMakeLists.txt` file reads in the chip configuration file, i.e. `stm32f1.cmake`, and create several basic targets for the project to boot up, like `bsp::startup`, `bsp::baremetal_linker` and `bsp::driver`. `bsp::driver` choose the HAL library or the LL library based on the cached variable `STM32_DRIVE_TYPE`, which is set by the preset in `CMakePresets.json` file.
- `cmake/stm32-utils.cmake` file contains some helper functions, like generating .bin and .hex files from the ELF file
  - The `compile_commands.json` file in the root folder is a symbolic link to the `compile_commands.json` file in the build folder, which is generated by CMake when building the project, because we may have multiple build folders for different configurations.
- `src/CMakeLists.txt` file contains the app logic for the project, and the `src/main.c` file is the main entry point of the project.
  - To build a runnable ELF, the project only needs to link `bsp::startup`, the driver you want to use, i.e. `bsp::driver`, and the linker options target `bsp::baremetal_linker`.

## Usage

### Switch to Different MCU Chip

To switch to a different MCU chip, you need to do the following steps:

- Add a new CMake file similar to `bsp/chip/stm32f1.cmake` for the new chip, specify required CPU flags, linker options and compile options, and offer an interface target `bsp::mcu_config`
- Check the offical ARM CMSIS, STM32 CMSIS and STM32 HAL repos to see if the name of the repo matches the config in `dependencies.cmake` file, also check the tag for those repos.
- Add a new preset in the `CMakePresets.json` file for the new chip, reference to the default preset.
- Copy the BSP files from the official STM32 repos like `cmsis-device-*` to the `bsp` folder, and modify them if necessary.
- Change the references to those BSP files and the reference to the new chip config file in the `bsp/CMakeLists.txt`.

Then hopefully this CMake configuration will find related dependencies automatically and build the project successfully.

## Some Notes

### Macro Passed to `stm32:ll` Library

Actually there's no conditional checks like `#ifdef USE_FULL_LL_DRIVER` inside ST's official Low-Layer (LL) driver sources.
However, STM32CubeMX with LL driver enabled generates code with this macro defined, so we also define it in the `CMakeLists.txt` file to be compatible with the generated code.
If you don't use STM32CubeMX to generate code, you can remove this macro definition in the `CMakeLists.txt` file.

Besides, `USE_HAL_DRIVER` is strictly required by the HAL driver sources, so `USE_FULL_LL_DRIVER` is widely adopted by the community as a matching architectural flag for conditional compilation like

```c
#if defined(USE_HAL_DRIVER)
    HAL_Delay(1000);
#elif defined(USE_FULL_LL_DRIVER)
    LL_mDelay(1000);
#endif
```
